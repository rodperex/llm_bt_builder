4. **BLACKBOARD**: Use SINGLE braces `{}` to read/write Blackboard variables in ports (e.g., port="{my_variable}"). DO NOT use double braces `{{}}`.
  - Never concatenate multiple blackboard variables inside one attribute (INVALID: `"{a},{b}"`, `"{x};{y}"`).
  - Never mix literals and blackboard placeholders in the same attribute (INVALID: `"Status: {a} and {b}"`).
  - If you need combined content, first write it into ONE output blackboard variable, then reference that single variable.
  - Do NOT invent helper blackboard variables (e.g., `combined_text`) unless they are declared in objective outputs or produced by a previous node in this step.
  - Do NOT use assignment/helper nodes unless they exist in ROBOT CUSTOM CAPABILITIES (for example, do not use `SetBlackboard` if it is not listed).
5. **INTER-STEP DATA FLOW (inputs / outputs) — STRICT CONTRACTS**:
   - The objective may declare `inputs:` and/or `outputs:` lists of plain blackboard variable identifiers.
   - `inputs`: blackboard keys already written by a PREVIOUS step. These variables ARE guaranteed to exist.
     Wire the relevant INPUT port of the node that reads this data to `{identifier}`.
     Example: if `inputs: [destination]`, the Navigate node should have `target="{destination}"`.
   - `outputs`: blackboard keys this step MUST write so that a FUTURE step can read them. These are
     MANDATORY CONTRACTS — the generated BT MUST write EXACTLY these variable names to the blackboard,
     using the exact spelling. Do NOT substitute them with different names even if the `steps:` description
     uses other names. Wire the relevant OUTPUT port of the node that produces this data to `{identifier}`.
    Example: if `outputs: [full_order]`, at least one node must map one of its output ports to
      `{full_order}`, e.g. `<DICTIONARY_NODE some_output_port="{full_order}"/>`.
     If the steps description suggests splitting into sub-variables (e.g. first_dish, second_dish),
     you may write those too as intermediate variables, but you MUST ALSO write the declared output key.
     Never write only the sub-variables and leave the declared output key unwritten.
   - Do NOT invent inputs or outputs that are not listed. Do NOT ignore listed ones.
   - If the objective also declares `available_blackboard_vars:`, those are variables already in the
     blackboard from previous steps. You may freely read them as inputs by wiring the relevant port.
6. **PARALLEL SUB-ACTIONS**:
   - The objective's `steps:` list may contain entries of two kinds:
     * Sequential: `- step: "<action>"` — map to a node inside the enclosing Sequence.
     * Parallel group: `- parallel:\n    - step: "<A>"\n    - step: "<B>"` — map to a
       `<Parallel success_count="N" failure_count="1">` node where N equals the number of
       children (i.e. all must succeed). Place the parallel group at the correct position
       inside the Sequence, preserving the overall ordering.
   - The sub-actions inside a `parallel:` group are causally independent; they do NOT share
     output ports with each other. Each sub-action maps to its own node inside `<Parallel>`.
   - Default to `<Sequence>` for everything. Only emit `<Parallel>` when the objective
     explicitly contains a `parallel:` group.
   - Example mapping:
     ```
     steps:
       - step: "Navigate to kitchen"
       - parallel:
           - step: "Speak order to chef"
           - step: "Activate display panel"
       - step: "Wait for acknowledgement"
     ```
     becomes:
     ```xml
     <Sequence>
       <DICTIONARY_NODE name="Navigate" target="kitchen"/>
       <Parallel success_count="2" failure_count="1">
         <DICTIONARY_NODE name="Speak" text="{order}"/>
         <DICTIONARY_NODE name="ActivateDisplay"/>
       </Parallel>
       <DICTIONARY_NODE name="WaitAck"/>
     </Sequence>
     ```

7.1 **STRING COMPOSITION SAFETY**:
  - If an input port expects one string and you need to express multiple fields, use a valid pattern with available capabilities only:
    1) one action call per field, or
    2) one action that natively supports list/enumeration input, fed from one valid input variable or literal.
  - Never emulate string templates inline with multiple `{vars}` inside one attribute.
  8. **CONDITION SEMANTICS AND FAILURE HANDLING**:
    - Condition nodes are boolean checks. Use them to gate behavior (typically inside `Sequence`, `Fallback`, or with decorators like `Inverter`).
    - Do not treat condition checks as standalone "do-and-continue" actions.
    - If the objective implies retry, correction, or recovery after a failed check, model explicit success and failure branches.
    - For recoverable checks, NEVER place a condition as a plain linear gate followed only by a success action. Model a control-flow branch: success child + failure recovery child.
    - `objective.recovery_policy.required=true` means the BT must include an explicit recovery branch, not just a retry decorator.
    - When eventual success is required, wrap the check+recovery branch with `RetryUntilSuccessful` (or equivalent loop control) so the tree retries after recovery instead of terminating on first failure.
    - Use `RetryUntilSuccessful` only when `objective.recovery_policy.required=true` or `objective.recovery_policy.loop_until_success=true`.
    - If both `required=false` and `loop_until_success=false`, do NOT add `RetryUntilSuccessful` around plain action sequences.
    - If objective.recovery_policy.retry_attempts is provided with a positive integer, you MUST set `RetryUntilSuccessful num_attempts` to exactly that value.
    - If objective.recovery_policy.retry_attempts is `forever`, use unbounded retry (`RetryUntilSuccessful num_attempts="-1"`).
    - Do NOT infer `required=true` only from the presence of retry_attempts. Plain action retries may use RetryUntilSuccessful without a separate recovery branch.
    - When a condition node exposes diagnostic outputs (for example, a list of failing elements), wire those outputs to blackboard variables and use them in the failure branch when relevant.
  9. **DATA CONSISTENCY**:
    - Keep distinct pieces of information in distinct blackboard variables unless the objective explicitly asks to merge them.
    - If the objective differentiates categories (for example type A vs type B information), preserve that separation in ports and variables throughout the BT.
    - Never overwrite a required output key with unrelated content.
  10. **LONG-RUNNING ACTIONS (CRITICAL)**:
    - Any action that can remain in `RUNNING` indefinitely (until externally halted/preempted) is non-terminating.
    - Reason in terms of tick-level progress: in a plain `<Sequence>`, if child *i* keeps returning `RUNNING`, children *i+1..N* are never ticked.
    - Therefore, do not place non-terminating actions in a position that prevents required downstream checks/actions from being ticked.
    - Place non-terminating actions under reactive control (`<ReactiveSequence>` or `<ReactiveFallback>`) together with the relevant checks/conditions.
    - For continuous behaviors that must stop on a condition, the guard condition must represent STOP/ABORT, not CONTINUE. If you only have a positive progress condition, invert it before using it as the guard.
    - For `<ReactiveFallback>`, place the stop condition first and the running action second; do not place a positive "keep going" condition as the first child.
    - For `<Sequence>`, do not place a non-terminating action before later siblings that still need to be ticked; use reactive control or reorder the flow.
    - **`<Repeat num_cycles="-1">` is non-terminating**: it never returns SUCCESS. NEVER place it inside control nodes.
  11. **PRE-RESPONSE SELF-CHECK (MANDATORY, GENERAL)**:
      - Before returning XML, verify all seven checks:
        1) Every leaf node tag exists in ROBOT CUSTOM CAPABILITIES.
        2) Every attribute used by a node is an allowed port for that same node.
        3) Every blackboard binding is either exactly one `{var}` token or a plain literal.
        4) Progress check: no plain `<Sequence>` contains a potentially non-terminating child before siblings that must still be ticked.
        5) Infinite-repeat check: no `<Repeat num_cycles="-1">` appears inside control nodes.
        6) Structural arity check: no empty control nodes and no decorators with zero or multiple children.
        7) Every control node has a meaningful non-empty `name` attribute in snake_case.
      - If any check fails, regenerate the XML from scratch. Do not patch by inventing helper nodes.
